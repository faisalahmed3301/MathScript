# MathScript Grammar

This is the complete, literal grammar MathScript hands to Bison
(`src/parser.y`). Nothing is simplified or omitted for this document --
it is generated by hand from the same rules the parser is built from,
and the running compiler will print the identical text via the
`/grammar` command, so "the grammar" is never just a diagram: it is
what actually executes.

```
input        -> CALC_MODE
             |  GRAPH_MODE
             |  EQN_MODE
             |  statement

statement    -> expr
             |  expr '=' expr

expr         -> expr '+' expr
             |  expr '-' expr
             |  expr '*' expr
             |  expr '/' expr
             |  expr '^' expr
             |  expr '<' expr
             |  expr '>' expr
             |  expr '>=' expr
             |  expr '<=' expr
             |  expr '==' expr
             |  expr '!=' expr
             |  '-' expr                      (unary minus)
             |  '(' expr ')'
             |  NUMBER
             |  IDENTIFIER
             |  IDENTIFIER '(' arglist ')'     (function call)

arglist      -> /* empty */
             |  expr
             |  arglist ',' expr
```

Precedence and associativity for the ambiguous `expr` rule are
declared separately -- see `docs/OPERATOR_PRECEDENCE.md`.

## Why one grammar for three modes

Earlier design drafts gave each mode its own top-level rule
(`calc_input -> expression`, `graph_input -> 'y' '=' expression`,
`eqn_input -> expression '=' expression`). Implementing that literally
turned out to need three copies of the same expression grammar. Instead,
`statement` already covers all three shapes:

| Mode    | What the user types      | Matches `statement` as        |
|---------|---------------------------|--------------------------------|
| `/calc` | `2 + 3 * 4`                | `expr`                         |
| `/calc` | `x = 10`                   | `expr '=' expr` (LHS is a var) |
| `/graph`| `y = x^2`                  | `expr '=' expr` (LHS is `y`)   |
| `/eqn`  | `x^2 - 5*x + 6 = 0`        | `expr '=' expr`                |

Bison parses the SAME statement shape in every mode; `main.c` looks at
which mode is currently active and dispatches the resulting AST to
`calc.c`, `graph.c`, or `solver.c` accordingly. Each backend then
applies its own semantic rule (e.g. `graph.c` requires the left side
of `=` to be the identifier `y`; `calc.c` requires it to be *some*
plain identifier). This keeps the grammar itself small while still
statically catching real syntax errors (`10 + * 5` is invalid in
every mode, and Bison rejects it before any mode-specific code runs).

## Tokens produced by the lexer (`src/lexer.l`)

| Token        | Matches                                  |
|--------------|-------------------------------------------|
| `CALC_MODE`  | `/calc`                                    |
| `GRAPH_MODE` | `/graph`                                   |
| `EQN_MODE`   | `/eqn`                                     |
| `NUMBER`     | `[0-9]+(\.[0-9]+)?`                        |
| `IDENTIFIER` | `[a-zA-Z_][a-zA-Z0-9_]*`                    |
| `GE LE EQ NE`| `>= <= == !=`                              |
| single chars | `+ - * / ^ = < > ( ) ,`                     |

Any other character is rejected by the lexer's catch-all rule with a
`Lexical Error`, before it ever reaches the parser.

## Where each grammar rule is implemented

| Compiler phase       | File            |
|-----------------------|-----------------|
| Tokens (lexer)        | `src/lexer.l`   |
| Grammar (parser)      | `src/parser.y`  |
| AST node types        | `src/ast.h/.c`  |
| Symbol table          | `src/symtab.h/.c` |
| Semantic checks       | inline in `src/eval.c` (unknown name/function, arity) |
| IR / Three-Address Code | `src/ir.h/.c` |
| `/calc` backend       | `src/calc.c`    |
| `/graph` backend      | `src/graph.c`   |
| `/eqn` backend        | `src/solver.c`  |
| Target code generation| `src/codegen.c` |
| Error reporting        | `src/errors.h/.c` |
| REPL / script driver  | `src/main.c`    |
